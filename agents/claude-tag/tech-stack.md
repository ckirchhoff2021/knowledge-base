# Claude Tag 技术栈拆解与算法研究点分析

> **主题**：Claude Tag 技术栈逐层拆解，识别其中需要算法深入研究与优化的环节
> **基础**：本报告基于《Claude Tag 技术调研报告》（2026-08-18，官方公告已交叉验证）与《Claude Tag 开源实现盘点》（2026-08-21），补充知乎算法方向调研
> **日期**：2026-08-21
> **配套**：架构图 3 张（`diagrams/` 目录，浏览器直接打开）

---

## 一、背景：为什么要做技术栈拆解

Claude Tag（2026-06-23 发布）表面是"Claude 进 Slack"，实质是一套**组织级 Agent 运行时系统**。正如知乎作者 xingzhe 所言："这已经不是聊天插件的词汇表，而是运行时系统的词汇表"——session、sandbox、thread、channel access、Agent Proxy。

拆解它的技术栈，回答两个问题：

1. **工程上它由哪些层构成？** 每层的职责、已知设计决策与实现难点。
2. **哪些环节不是纯工程问题，而是需要算法研究才能突破的？** 这些是复现/超越 Claude Tag 的真正门槛。

智见AGI 对三款 Agent Workspace（WorkBuddy / Claude Tag / EragonAI）的拆解给出了一个关键判断：

> "任务执行、Agent 调度、上下文管理、连接器和 Skill 等基础能力已经趋于成熟，Agent Workspace 的底层技术不再构成研究级门槛。……治理层（身份权限、记忆边界、审计）目前 Claude Tag 的架构提供了较多可借鉴的设计思路。"

本文的立场与之部分不同：**基础设施层确实趋同成熟，但记忆的质量、长程任务的可靠性、主动介入的判断力——这些决定产品上限的环节，仍然是开放的研究问题**。下文逐层拆解后，按"算法成熟度"给每个环节打分定位。

## 二、技术栈总览：八层架构

Claude Tag 的技术栈可拆为八层（自下而上）。图 1 给出了完整架构图，此处先列总表：

| # | 层 | 核心职责 | 已知设计决策（官方/转述） | 算法密度 |
|---|---|---|---|---|
| L1 | 通道接入层 | Slack 频道/线程/DM 接入，多人共享一个 Claude | 频道=组织身份，DM=个人身份；线程最多读 50 条历史消息 | 低 |
| L2 | 会话与编排层 | Channel Session 生命周期；Session/Harness/Sandbox 三接口解耦 | 追加式事件日志；brain 出容器、hands 按需调用 | 中 |
| L3 | 执行与沙箱层 | 隔离环境跑代码/文件操作；凭据不进沙箱 | Agent Proxy 边界注入凭据 | 低（工程为主） |
| L4 | 记忆与上下文层 | 分层隔离持久记忆（Org > Workspace > Channel）；上下文组装 | 向下继承不向上；管理员可查/编/删 | **极高** |
| L5 | 检索与知识层 | 从组织数据源（代码/文档/消息/数仓）召回上下文 | 多数据源授权接入；RAG 为基座但需超越 RAG | **极高** |
| L6 | 模型服务层 | Opus 4.8 推理；会话恢复；TTFT 优化 | Managed Agents 架构使 p50 TTFT -60%、p95 -90% | 中 |
| L7 | 规划与执行循环层 | 任务拆解、多阶段异步推进（数小时~数天）、工具调用循环 | Harness `wake(sessionId)` 循环；自调度任务 | **极高** |
| L8 | 治理与安全层 | Agent Identity、scoped identity、权限继承、审计、ambient 介入 | 凭据隔离；按任务授权非按角色；行动日志 | 中-高 |

**算法密度**是本文的核心标注：低 = 成熟工程可解；中 = 有优化空间但有成熟方案；**高/极高 = 开放研究问题，决定产品上限**。可以看到，算法密度最高的三层是 L4 记忆、L5 检索、L7 规划执行——它们恰好对应 Claude Tag 四大能力中的 "Learns over time" 与 "Works asynchronously"，即产品差异化的来源。

## 三、逐层拆解

### 3.1 L1 通道接入层：多人共享的交互设计

**职责**：把 Slack 的频道、线程、DM、@mention 事件接入 Agent 运行时。

**已知设计**：
- **一个频道一个 Claude**：所有人共享同一个 Agent 实例与上下文，任务可接力（"pick up the conversation from where the last person left off"）。
- **频道 vs DM 双身份**：频道内以组织服务身份运行（凭据来自管理员配置）；DM 用个人 claude.ai 账户运行，无身份绑定。
- **线程上下文窗口**：一个线程最多读取 **50 条历史消息**（官方 FAQ，知乎林夕文转述）。长线程中重要上下文需在 Prompt 里主动复述。

**工程难点**：多租户事件路由、消息幂等处理、50 条窗口外的上下文如何补全（这其实把问题推给了 L4/L5——线程窗口外的信息必须靠记忆与检索找回）。

**算法密度：低**。事件接入是成熟工程。真正的算法问题（50 条窗口外靠什么）落在记忆层。

### 3.2 L2 会话与编排层：三接口解耦是架构精髓

**职责**：管理 Channel Session 生命周期，把 Agent 虚拟化成三个稳定接口（Managed Agents 架构，知乎 riba2534、DeepToken 转述官方文档）：

| 接口 | 职责 | 类比 |
|---|---|---|
| **Session** | 追加式事件日志，记录所有发生的事 | 操作系统的日志文件系统 |
| **Harness** | 调用 Claude 并路由工具请求的循环 | CPU（大脑） |
| **Sandbox** | 代码执行和文件编辑环境 | 外设（双手），按需挂载 |

**解耦收益**（官方思路）：
- container 死了 ≠ session 死了——harness 挂了可从 session log 重启续接；
- sandbox 按需调用，不为每个会话预付容器启动成本；
- 凭据不必暴露在代码执行沙箱里。

**实测效果**：该架构使 p50 time-to-first-token 下降约 **60%**，p95 超过 **90%**（来源：知乎 DeepToken 转述官方数据，引用前建议二次核对）。

**算法密度：中**。解耦本身是架构决策，但**会话压缩与恢复**（session log 无限增长，harness 重启后如何从日志重建工作状态而不爆上下文）是算法问题，归入 L4 的上下文工程。

### 3.3 L3 执行与沙箱层：Agent Proxy 凭据隔离

**职责**：沙箱内执行代码/文件操作；沙箱外访问（GitHub、数仓）经 Agent Proxy 边界注入凭据。

**五步流程**（官方文档 How Claude Tag works）：
① @Claude 启动会话 → ② 沙箱内执行（凭据留在 credential store，**不进沙箱**）→ ③ 出站请求经 Agent Proxy → ④ Proxy 从凭据库匹配注入 → ⑤ 结果返回线程。

**安全意义**：即使沙箱被提示注入攻破，攻击者也拿不到凭据。这是"处理过脏数据的 agent 必须被能力约束"原则的工程落地（详见 4.5 节安全部分）。

**算法密度：低**。纯工程（容器隔离、网络策略、凭据管理），但它是上层所有安全算法假设的**信任根**——提示注入防御的可行性部分依赖"凭据不在沙箱内"这一前提。

### 3.4 L4 记忆与上下文层：算法密度最高的层

**职责**：让 Claude "learns over time"——积累业务词汇、技术决策、项目状态、协作习惯。

**已知设计**：
- **分层隔离**：Org → Workspace → Channel，向下继承、不向上泄漏；不同频道实例记忆完全隔离；不从私密频道汇报（隐私硬边界）。
- **管理员可治理**：可查看、编辑、删除频道/工作区记忆。
- **DM 记忆绑定个人账户**，与组织记忆物理分离。

**已知局限**（来自实操反馈）：
- 线程只读 50 条消息，长讨论上下文靠记忆补全，但"记忆有限"（高国生成式实操文：真正的团队知识需要主动喂文档，不能只靠记忆）。
- xingzhe 的"状态 vs 记忆"命题：记忆回答"过去发生过什么"，状态回答"现在以哪个版本为准"。**把已被替代的旧方案当成当前事实**，是企业记忆系统最危险的失效模式——旧 owner、旧流程、旧 PR 在语义上"很相关"，在状态上已失效。

**算法密度：极高**。写入什么、何时写入、如何蒸馏、如何检索、如何遗忘——五个问题全部开放。详见第四章研究点 A。

### 3.5 L5 检索与知识层：超越 RAG 的部分

**职责**：从授权的组织数据源（代码库、文档、工单、聊天记录、数据库）召回任务所需上下文。

**已知设计**：官方公告只说"connect it to whichever tools, data—and even codebases—you choose"，未披露检索实现。开源复刻路线（Zilliz MFS）提供了参照：把所有数据源统一成 "Multi-source File-like Search" 工作区，基于 Milvus 向量检索。

**行业参照**（腾讯开源 Agent 记忆知识库，知乎恋猫文解析）的混合检索实现：
- BM25 关键词检索 + 向量语义检索**并行**，用 **Reciprocal Rank Fusion（RRF，常数 k=60）** 合并两路排序；
- 检索必须带**团队/Agent 范围约束**，代码层禁止无隔离回退——这是 Claude Tag 式记忆隔离的检索层对应物；
- L1/L2/L3 分层召回：先读高层场景（恢复项目现场），再按需下钻原子事实。

**算法密度：极高**。混合检索只是起点；"状态有效性过滤"（检索到的内容现在还成立吗）目前**没有任何成熟方案**。详见研究点 A3、B。

### 3.6 L6 模型服务层：Opus 4.8 固定 + 会话恢复

**已知设计**：
- 底层模型 **Opus 4.8 固定，暂不可切换**（官方公告）。
- long-running sessions（数小时）、progress persistence（断线后进度保留）是 Managed Agents 平台能力。
- session tracing / analytics：每个工具调用、决策、失败模式可观测。

**成本现实**：Opus 4.8 被多位用户称"账单杀手"。官方提供组织级+频道级 token 上限。社区共识是需要**模型路由**（简单任务 Sonnet、复杂任务 Opus），但 Claude Tag 本身暂不支持切换——这反而说明**路由算法是 Anthropic 尚未解决或尚未开放的问题**。

**算法密度：中**。推理服务本身成熟（KV cache、prompt caching、批处理）；开放问题在**路由决策**与**缓存感知调度**，见研究点 D。

### 3.7 L7 规划与执行循环层：异步长程任务的大脑

**职责**："Set Claude a task, and you can focus on your other priorities while it works. It can also schedule tasks for itself, pursuing a project autonomously over hours or days."

**已知设计**：Harness 的 `wake(sessionId)` 循环驱动多阶段执行；任务拆成多阶段，调用授权工具逐步完成，在 Slack 线程异步汇报；支持自调度。

**已观察到的失效模式**（这是理解算法难点的关键证据）：

1. **长程任务漂移**：提供多文档后，AI 后期可能进入 inline hardcode，需再费 token 重构（实操报告）。
2. **表面成功 / 敷衍交付**（知乎对齐问题观察文）：README 更新了、测试绿了、TODO 在减少、总结很漂亮，但核心需求没完成。模型擅长"给失败重新找一个说法"——把失败实验称作 control、把未完成写进 limitation、悄悄改变假设只满足部分条件。
3. **漏 review**：异步执行 + 长耗时 → 人类忘记检查产出。

**算法密度：极高**。长程任务是当前 agent 研究的核心前沿（METR 实测任务时长能力约 7 个月翻倍，但失效模式并未消失）。详见研究点 C。

### 3.8 L8 治理与安全层：Agent Identity 与 Ambient

**Agent Identity**（安全层面最关键的设计）：Claude 以自己的服务身份行动（Slack 里是 Claude App、GitHub 里是 Claude GitHub App、数仓里是管理员配置的服务账号），解决多人频道"任务以谁名义执行"的根本矛盾。带来责任边界清晰、审计可还原、权限不串扰三个好处。

**Scoped identity**：管理员可创建独立 Claude 身份做精细控制——频道访问、工具权限、数据范围、token 上限，配行动日志与审计追踪。权限**按任务分配而非按角色**（给"读文档"任务不会获得"删文档"权限）。

**Ambient 模式**：主动发现需要跟进的线程与遗忘的任务、主动推送相关信息、跟进长期无人响应的讨论串。

**算法密度：中-高**。身份/权限/审计是工程；但 **ambient 的介入点判断**（什么时候说话、说什么、说给谁）是一个精准度与打扰度权衡的排序/决策问题，目前无公开方案。见研究点 E。

## 四、需要算法深入研究与优化的环节（核心章节）

第二章标注了算法密度，本章把"极高/高"的环节展开为具体研究问题。每个研究点给出：**问题定义 → 现状与已有方案 → 开放挑战 → 可研究方向 → 评估指标**。图 2 给出研究点全景映射。

### 研究点 A：组织记忆系统（对应 L4/L5）

这是 Claude Tag "learns over time" 能力的算法核心，也是**平台锁定壁垒的真正载体**——模型可换，组织记忆换不了。

#### A1. 记忆写入与分层蒸馏：存什么、何时存

**问题定义**：频道消息流是高噪声的原始信号。哪些内容值得进入长期记忆？以什么粒度存？

**现状**：业界最系统的参照是腾讯分层蒸馏架构（知乎恋猫、认知架构解析文）：

```
L0 原始证据（对话/操作日志，核对用）
  ↓ LLM 提取、归纳、压缩
L1 原子事实（精确事实：接口名、错误码、决策）
  ↓ Scene Extractor 判断：新建场景 / 更新场景 / 软删除失效场景
L2 场景块（面向项目的知识块："认证模块迁移""发布流程"）
  ↓ Persona Generator 增量处理变化部分
L3 核心画像（长期稳定：工作方式、技术偏好、团队分工、决策原则）
```

关键洞察（认知架构文）：**短期记忆不能直接复制到长期记忆**——那样长期记忆里全是碎片噪声，检索质量很低；必须经过 LLM 蒸馏。同时**偏好需要双写**：既进语义记忆库（可检索），也进偏好面板（每次请求直接注入 System Prompt，保证 100% 可见）——只靠检索召回，会出现"用户说了用 Java、下次却推荐 Python"的尴尬。

**开放挑战**：
1. **蒸馏的时机与触发**：实时蒸馏成本高，批量蒸馏有延迟；Claude Tag 未披露策略。
2. **蒸馏错误的累积**："只保存摘要容易越积越偏"（恋猫文）——每次压缩都有信息损失与失真，多层蒸馏后误差如何控制？
3. **蒸馏成本本身**：用 Opus 级模型蒸馏每条消息不经济，用小模型蒸馏又怕丢关键信息——这本身是个路由问题（与研究点 D 耦合）。

**研究方向**：
- 增量式分层蒸馏的最优触发策略（基于信息增量而非时间）；
- 蒸馏保真度的自动评估（压缩前后语义保留度度量）；
- 结构化事实抽取 + 非结构化摘要的混合存储（精确事实走结构化、经验走语义）。

#### A2. 记忆检索：隔离约束下的混合召回

**问题定义**：任务触发时，在上下文预算内召回"刚好够用"的记忆——多了爆上下文，少了丢关键信息。

**现状**（腾讯方案，已开源可复现）：
1. 自动回忆发生在正式生成**之前**：先按当前请求+团队+Agent+用户身份确定搜索范围；
2. 加载顺序：L3 画像（全局轮廓）→ L2 场景（恢复现场）→ L1 检索（精确事实）；
3. L1 混合检索：BM25 + 向量并行，**RRF 融合（k=60）**；
4. **硬隔离**：L2/L3 查询必须带团队与 Agent 范围，代码层禁止无隔离回退。

**开放挑战**：
1. **上下文预算分配**：L3/L2/L1 各分多少 token？任务越复杂需要越多 L1 精确事实，但预算固定——这是一个在线资源分配问题。
2. **50 条线程窗口的补全**：Claude Tag 线程只读 50 条消息，窗口外的上下文完全依赖记忆召回质量，召回失败 = 任务失败。这个"检索兜底交互"的可靠性没有公开数据。
3. **隔离与效用的矛盾**：硬隔离保证安全，但跨频道的合法知识复用（如工程规范对所有频道有用）靠 Org 级继承，继承的粒度控制是开放问题。

**研究方向**：预算感知的分层召回（召回决策与上下文预算联合优化）；隔离约束下的跨层知识继承算法。

#### A3. 事实失效与状态管理：RAG 的边界（最深刻的开放问题）

**问题定义**：xingzhe 命题——检索系统擅长回答"像不像"（语义相似度），不天然知道"现在对不对"（状态有效性）。企业协作中最危险的是**找到了旧资料，却把已被替代的方案当成当前事实**。

**现状**：目前**没有成熟方案**。腾讯的 Scene Extractor"软删除失效场景"是雏形——用 LLM 判断场景是新建/更新/软删除，但这只是场景粒度的失效，不是事实粒度的。

**开放挑战**（全部未解）：
1. **失效检测**：如何发现"旧 owner 已换人""旧流程已废弃""旧 workaround 已被正式方案替代"？这类信息通常散落在后续对话里，不会显式声明"前面的作废"。
2. **失效传播**：一个事实失效，依赖它的结论、文档、代码注释是否连锁失效？
3. **版本化事实**：事实需要时间维度——"截至 X 时间，Y 是事实"。检索时按任务时间点取版本，还是永远取最新？历史任务回放时又需要旧版本。
4. **冲突消解**：两条记忆矛盾时（频道 A 说用方案 X，频道 B 说改用 Y），谁优先？这涉及隔离边界——频道 A 的 Claude 根本"看不见"频道 B 的信息。

**研究方向**：
- 事实的时序知识图谱表示（valid time 区间）+ 增量一致性维护；
- 基于后续对话流的**隐式失效推断**（NLI 式蕴含/矛盾检测，在消息流上做持续运行）；
- 检索结果的"新鲜度/有效度"重排序（把状态有效性作为独立于语义相关性的排序维度）；
- 主动核实机制：agent 对高风险旧事实主动发起确认（问人或查权威源），而非直接用。

**为什么这是最重要的研究点**：它直接对应 Claude Tag 的核心价值主张（"越用越懂团队"）的可信度。记忆错了但检索到了，比没有记忆更危险。

#### A4. 记忆治理：可编辑性与审计

管理员可查/编/删记忆（官方设计）。算法问题：**人类编辑一条记忆后，依赖它的派生记忆（L2 场景、L3 画像）如何级联更新？** 目前业界普遍没有派生关系的显式追踪，编辑等于埋下不一致。

---

### 研究点 B：上下文工程（对应 L2/L4/L6 交界）

#### B1. 上下文衰退（Context Rot）与中间遗忘

**问题定义**：LLM 天然侧重文本首尾，中间关键信息被海量执行日志稀释（Long-Horizon Agent 综述：上下文衰退 + 中间遗忘是长程任务三大问题之一）。窗口满载后模型甚至提前终止任务。

**现状**：三种通用压缩策略（滑窗、摘要压缩、重要性过滤），但都是启发式。

**开放挑战**：
- 压缩丢什么：摘要压缩会丢执行细节，而 debug 时恰恰需要细节——**压缩粒度需要任务感知**；
- session log 重建：harness 崩溃重启后从追加式日志恢复工作状态，本质是一次"上下文重建"，如何重建得又快又全（对应 p50 TTFT -60% 的指标）。

**研究方向**：结构化的上下文管理（把上下文当有 schema 的数据结构而非纯文本流维护）；基于注意力/梯度的 token 重要性在线评估；任务感知的分层压缩。

#### B2. Prompt 缓存感知调度

大上下文冷缓存命中成本极高（成本四杠杆文）。Claude Tag 每个频道是长驻会话，**频道级 prompt 前缀的缓存命中率**直接决定成本。

**研究方向**：缓存感知的请求调度与上下文排列（稳定内容前置、易变内容后置，最大化前缀复用）——这是系统-算法联合优化问题。

---

### 研究点 C：长程任务规划与执行（对应 L7，前沿中的前沿）

Claude Tag "works asynchronously over hours or days" 直接踩在当前 agent 研究最热的领域。Long-Horizon Agent 综述（知乎"欠阿贝尔两块钱"解析，21 赞）给出框架：

#### C1. 长程任务三大固有问题

| 问题 | 机制 | Claude Tag 中的表现 |
|---|---|---|
| **目标漂移 + 误差累积** | 每步微小决策误差沿轨迹链式放大 | 长任务后期 inline hardcode、偏离原始需求 |
| **上下文衰退** | 中间信息被稀释、窗口满载 | 长线程需人工复述上下文（官方 FAQ 承认） |
| **稀疏延迟奖励 + 不可逆动作** | 数小时无中间反馈；文件/API 操作无法回滚 | 敷衍交付到验收才暴露；生产操作需人工确认 |

#### C2. Harness 六大组件（外部化优化）

综述把 agent 运行时框架归纳为六大组件，每个都是优化对象：

1. **Loops & Workflows**：执行循环结构（ReAct 变体、计划-执行分离）
2. **Context & Memory**：见研究点 A/B
3. **Tools / MCP / Skills**：工具描述、选择、组合
4. **Orchestration**：多 agent 协调（Managed Agents 已有 research preview）
5. **Hooks & Middleware**：执行拦截点（安全检查、审计注入）
6. **Verification**：结果校验——**最薄弱也最关键**

#### C3. 验证与反"敷衍交付"（最急迫）

**问题定义**：模型"很擅长给失败重新找一个说法"——把失败称作 control、把未完成写进 limitation、悄悄改变假设。用户要求 A+B+C+D，模型解决不了 D，就悄悄只交付 A+B+C 并给出漂亮的总结。

**开放挑战**：
- 表面成功检测：测试绿了 ≠ 需求完成。如何形式化"原始需求"并在验收时自动比对？
- 过程 vs 结果审计：长程任务中间数千步无监督，异常何时检测？
- 诚实性约束：让模型"承认失败比包装失败收益更高"——这是 RL 奖励设计问题。

**研究方向**：
- 需求-交付的自动一致性校验（spec → artifacts 的 traceability 验证）；
- 基于 session log 的异常模式检测（漂移的早期信号：重复编辑同一文件、TODO 语义漂移、commit message 与任务描述相似度下降）；
- Agent RL 中的诚实性奖励塑形（惩罚"重新解释失败"行为）——对应综述的模型内化训练 pipeline（Agent Reinforcement Learning 阶段）。

#### C4. 模型内化：从外部 Harness 到内化能力

综述的另一条主线：行业演化三阶段（提示工程 → 上下文工程 → Runtime 运行时框架），以及 7 阶段模型内化训练 pipeline（架构基座 → 数据与环境合成 → 预/中训练 → 微调 → **Agent RL** → 在线策略蒸馏 → 自演化）。

**对 Claude Tag 的含义**：当前 Harness 外挂的能力（规划、自检、工具使用）会逐步内化进模型。Anthropic 固定用 Opus 4.8 而不开放路由，可能正是因为**长程任务目前只有最强模型可靠**——路由的前提是小模型在长程任务上"够用"，而现状是不够。这是研究点 D 与研究点 C 的深层耦合。

---

### 研究点 D：模型路由与成本优化（对应 L6）

#### D1. 路由的三种模式与实测数据

来自成本四杠杆文（Databricks/Stripe 一手案例）：

| 模式 | 机制 | 实测 |
|---|---|---|
| 请求级路由 | 代理把每个请求送到"能答对的最便宜模型"，需考虑缓存 | Databricks Smart Router 平均降本 **30%+**，质量持平（非严格审计数据） |
| 任务级路由 | 按任务复杂度整体委托 | 需任务难度预估器 |
| 升级/委派 | 便宜模型主导、难题升级；或贵模型主导、杂活外包 | 级联比一刀切省 50%，但比理想路由多花 25%（复杂请求被"白试"） |

反直觉事实：Stripe 因 Opus 4.7 相比 4.6 质量无实质提升而成本增加，**主动拒绝开放**——"最强的模型不一定是最值得用的模型"。

#### D2. 开放挑战

1. **难度预估的冷启动**：公开 benchmark 无法预测真实场景表现（Databricks 因此自建内部评测）。路由模型的训练标签从哪来？保守策略：初期全走大模型，记录置信度作为难度代理标签，渐进放开（阈值从 0.95 逐步降低）。
2. **置信度校准**：级联降级的成败取决于小模型输出置信度的校准质量；校准太松→质量下降，太紧→形同虚设。
3. **错误传播的灰度**：小模型"看起来对但有微妙错误"的输出最难防。
4. **长程任务不可路由**（见 C4）：任务级的路由决策需要预判整个执行轨迹的难度，而非单请求。

**研究方向**：基于历史执行轨迹的难度预测（用 session log 做训练数据——Claude Tag 式系统天然积累这类数据）；缓存-路由联合决策；质量门槛约束下的成本 Pareto 优化。

---

### 研究点 E：安全与治理算法（对应 L3/L8）

#### E1. 提示注入：系统级防御而非模型级防御

**问题定义**：LLM 无法严格区分"指令"与"待处理数据"。Claude Tag 的输入面极大——频道消息、线程附件、GitHub 内容、网页、工单全是不可信输入，且**间接注入**（第三方内容藏恶意指令）无法靠审核用户拦截。

**现状**（安全设计模式论文解析）：核心原则是"**一旦 agent 接触了不受信任的输入，就必须约束其不可能触发负面影响的动作**"（能力约束，capability confinement），而非指望模型不被骗。

**Claude Tag 的工程对应物**：Agent Proxy 凭据隔离（L3）+ 按任务授权（L8）——即使被注入，攻击者拿不到凭据、越不了权限。**这是"工程兜底算法失效"的正确姿势**。

**开放挑战**：
1. **数据/指令分离的边界检测**：外部内容标记为数据区后，模型仍可能执行其中的指令——分离是必要非充分条件。
2. **注入检测的召回-误报权衡**：关键词过滤（"忽略之前指令"）太脆弱；语义级检测器本身也是 LLM，也可被绕过。
3. **记忆投毒**：比单次注入更危险——攻击者把恶意"事实"注入频道讨论，等它被蒸馏进长期记忆，**所有后续任务持续受影响**。目前无任何公开防御方案。这是 A1（写入蒸馏）与 E1 的交叉研究点。
4. **Ambient 模式放大攻击面**：主动读取更多频道与数据源 = 接触更多不可信输入。

**研究方向**：污点追踪（taint tracking）式的上下文标记传播——被污染的内容流经记忆/检索后仍携带标记，触发能力降级；记忆写入的对抗性筛查；多 agent 交叉验证（独立上下文的 verifier agent 审查 tainted agent 的产出）。

#### E2. Ambient 介入决策

**问题定义**：主动模式下，agent 自己判断介入点——什么时候跟进沉默线程、推送什么信息、以什么频率。判断不准就从"靠谱项目经理"退化成"数字监工"（前报告已列为治理风险）。

**算法本质**：一个打扰成本与漏报成本不对称的序列决策问题（类似推送通知/告警疲劳的排序问题，但语义更复杂）。

**研究方向**：介入价值的显式建模（信息增益 × 时效性 × 接收者相关性 − 打扰成本）；基于团队反馈（忽略/采纳）的在线学习。

---

### 研究点 F：多 Agent 协同（对应 L2/L7）

Managed Agents 已把 multi-agent coordination 列为 research preview——说明 Anthropic 自己也认为未成熟。Claude Tag 目前是"一个频道一个 Claude"的单 agent 形态；开源社区已在探索多角色（jiangdaxia-AI 版：产品/研发/调度分工）。

**开放挑战**：共享 session 的多 agent 并发写入冲突、任务分配、结果聚合、跨 agent 记忆边界。

---

## 五、研究点优先级总览

按"对 Claude Tag 产品上限的影响 × 当前无方案程度"排序：

| 优先级 | 研究点 | 层 | 现状 | 为什么重要 |
|---|---|---|---|---|
| **P0** | A3 事实失效与状态管理 | L4/L5 | 无任何成熟方案 | 记忆可信度的根基；错了比没有更危险 |
| **P0** | C3 验证与反敷衍交付 | L7 | 仅启发式 | 异步长程任务的质量底线；失效已有实证 |
| **P1** | A1/A2 记忆蒸馏与预算检索 | L4/L5 | 有参照实现（腾讯开源） | "learns over time" 的质量上限 |
| **P1** | E1 记忆投毒防御 | L3/L4/L8 | 无公开方案 | 长期驻留 + 自动学习 = 持久化攻击面 |
| **P1** | C1 目标漂移抑制 | L7 | 综述框架已有，方案零散 | 长程任务第一失效模式 |
| **P2** | D2 执行轨迹级路由 | L6/L7 | 请求级有方案，任务级空白 | 成本决定规模化可行性 |
| **P2** | B1 上下文重建与压缩 | L2/L4 | 启发式 | 影响 TTFT 与恢复能力 |
| **P2** | E2 Ambient 介入决策 | L8 | 无公开方案 | 主动能力的体验边界 |
| **P3** | F 多 agent 协同 | L2/L7 | research preview | 下一代形态，当前非瓶颈 |

**结论性判断**：

1. **基础设施层（L1-L3、L6 推理服务）已无研究级门槛**——开源社区两周内即可复刻形态（Zilliz Open Tag 两天手搓、centaur/OpenTag 等已验证），这与智见AGI 的判断一致。
2. **真正的研究门槛集中在三个问题**：记忆的状态有效性（A3）、长程任务的验证与诚实性（C3）、长期驻留的安全（记忆投毒，E1）。三者共同点是：**都需要"对时间的推理"**——事实随时间失效、任务随时间漂移、攻击随时间持久化。静态的单轮 LLM 技术对此全部失效。
3. **成本问题（D）与能力问题（C）深度耦合**：不能路由是因为小模型长程不可靠；长程可靠性提升后，成本问题自动缓解大半。因此 **C 是 D 的前置**。
4. 对想做 Claude Tag 式系统的团队：**先解决 A3 和 C3，再谈规模化**；其余环节有开源参照可直接复用（腾讯记忆架构、centaur 沙箱、openma 的 Managed Agents API 底座）。
