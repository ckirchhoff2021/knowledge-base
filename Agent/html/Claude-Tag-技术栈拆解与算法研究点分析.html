一、背景：为什么要做技术栈拆解

Claude Tag（2026-06-23 发布）表面是"Claude 进 Slack"，实质是一套组织级 Agent 运行时系统。正如知乎作者 xingzhe 所言："这已经不是聊天插件的词汇表，而是运行时系统的词汇表"——session、sandbox、thread、channel access、Agent Proxy。

拆解它的技术栈，回答两个问题：

  1. 工程上它由哪些层构成？每层的职责、已知设计决策与实现难点。
  2. 哪些环节不是纯工程问题，而是需要算法研究才能突破的？这些是复现/超越 Claude Tag 的真正门槛。
智见AGI 对三款 Agent Workspace（WorkBuddy / Claude Tag / EragonAI）拆解的核心发现："任务执行、Agent 调度、上下文管理、连接器和 Skill 等基础能力已经趋于成熟，Agent Workspace 的底层技术不再构成研究级门槛。……治理层（身份权限、记忆边界、审计）目前 Claude Tag 的架构提供了较多可借鉴的设计思路。"
本文立场
基础设施层确实趋同成熟，但记忆的质量、长程任务的可靠性、主动介入的判断力——这些决定产品上限的环节，仍然是开放的研究问题。下文逐层拆解后，按"算法密度"给每个环节打分定位。

二、技术栈总览：八层架构

Claude Tag 的技术栈可拆为八层（自下而上）：

#层核心职责已知设计决策（官方/转述）算法密度
L1通道接入层Slack 频道/线程/DM 接入，多人共享一个 Claude频道=组织身份，DM=个人身份；线程最多读 50 条历史消息低
L2会话与编排层Channel Session 生命周期；三接口解耦追加式事件日志；brain 出容器、hands 按需调用中
L3执行与沙箱层隔离环境跑代码；凭据不进沙箱Agent Proxy 边界注入凭据低（工程为主）
L4记忆与上下文层分层隔离持久记忆（Org > Workspace > Channel）向下继承不向上；管理员可查/编/删极高
L5检索与知识层从组织数据源召回上下文多数据源授权接入；RAG 为基座但需超越 RAG极高
L6模型服务层Opus 4.8 推理；会话恢复；TTFT 优化Managed Agents 架构使 p50 TTFT -60%、p95 -90%中
L7规划与执行循环层任务拆解、多阶段异步推进（小时~天）Harness wake(sessionId) 循环；自调度任务极高
L8治理与安全层Agent Identity、scoped identity、审计、ambient凭据隔离；按任务授权非按角色；行动日志中-高

三、逐层拆解

3.1 L1 通道接入层：多人共享的交互设计

  • 一个频道一个 Claude：所有人共享同一个 Agent 实例与上下文，任务可接力（"pick up the conversation from where the last person left off"）。
  • 频道 vs DM 双身份：频道内以组织服务身份运行（凭据来自管理员配置）；DM 用个人 claude.ai 账户运行。
  • 线程上下文窗口：一个线程最多读取 50 条历史消息（官方 FAQ，知乎林夕文转述）。长线程中重要上下文需在 Prompt 里主动复述——这把问题推给了 L4/L5：窗口外的信息必须靠记忆与检索找回。

算法密度：低。事件接入是成熟工程；真正的算法问题落在记忆层。

3.2 L2 会话与编排层：三接口解耦是架构精髓

接口职责类比
Session追加式事件日志，记录所有发生的事日志文件系统
Harness调用 Claude 并路由工具请求的循环CPU（大脑）
Sandbox代码执行和文件编辑环境外设（双手），按需挂载

解耦收益：container 死了 ≠ session 死了；harness 挂了可从 session log 重启续接；sandbox 按需调用不预付容器成本；凭据不必暴露在沙箱里。

实测效果：p50 time-to-first-token 下降约 60%，p95 超过 90%（知乎 DeepToken 转述官方数据，引用前建议二次核对）。

算法密度：中。解耦是架构决策，但会话压缩与恢复（session log 无限增长，重启后如何重建工作状态而不爆上下文）是算法问题。

3.3 L3 执行与沙箱层：Agent Proxy 凭据隔离

五步流程：① @Claude 启动会话 → ② 沙箱内执行（凭据留在 credential store，不进沙箱）→ ③ 出站请求经 Agent Proxy → ④ Proxy 从凭据库匹配注入 → ⑤ 结果返回线程。

安全意义：即使沙箱被提示注入攻破，攻击者也拿不到凭据。这是上层所有安全算法假设的信任根。

算法密度：低（纯工程：容器隔离、网络策略、凭据管理）。

3.4 L4 记忆与上下文层：算法密度最高的层

  • 分层隔离：Org → Workspace → Channel，向下继承、不向上泄漏；不同频道实例记忆完全隔离；不从私密频道汇报（隐私硬边界）。
  • 管理员可治理：可查看、编辑、删除频道/工作区记忆。
  • 已知局限：线程只读 50 条消息；"记忆有限"（实操反馈：真正的团队知识需要主动喂文档）。
xingzhe 的"状态 vs 记忆"命题：记忆回答"过去发生过什么"，状态回答"现在以哪个版本为准"。把已被替代的旧方案当成当前事实，是企业记忆系统最危险的失效模式——旧 owner、旧流程、旧 PR 在语义上"很相关"，在状态上已失效。

算法密度：极高。写入什么、何时写入、如何蒸馏、如何检索、如何遗忘——五个问题全部开放。详见第四章研究点 A。

3.5 L5 检索与知识层：超越 RAG 的部分

官方未披露检索实现。开源复刻路线（Zilliz MFS）参照：把所有数据源统一成 "Multi-source File-like Search" 工作区，基于 Milvus 向量检索。

行业参照（腾讯开源 Agent 记忆知识库）的混合检索实现：

  • BM25 关键词检索 + 向量语义检索并行，用 Reciprocal Rank Fusion（RRF，常数 k=60） 合并两路排序；
  • 检索必须带团队/Agent 范围约束，代码层禁止无隔离回退；
  • 分层召回：先读高层场景（恢复项目现场），再按需下钻原子事实。

算法密度：极高。"状态有效性过滤"目前没有任何成熟方案。详见研究点 A3、B。

3.6 L6 模型服务层：Opus 4.8 固定 + 会话恢复

  • 底层模型 Opus 4.8 固定，暂不可切换（官方公告）。
  • long-running sessions（数小时）、progress persistence（断线后进度保留）、session tracing / analytics。
  • 成本现实：Opus 4.8 被称"账单杀手"。社区共识需要模型路由（简单任务 Sonnet、复杂任务 Opus），但 Claude Tag 暂不支持——这反而说明路由算法是 Anthropic 尚未解决或尚未开放的问题。

算法密度：中。开放问题在路由决策与缓存感知调度（研究点 D）。

3.7 L7 规划与执行循环层：异步长程任务的大脑

"Set Claude a task, and you can focus on your other priorities while it works. It can also schedule tasks for itself, pursuing a project autonomously over hours or days."

已观察到的失效模式（理解算法难点的关键证据）：

  1. 长程任务漂移：提供多文档后，AI 后期可能进入 inline hardcode，需再费 token 重构。
  2. 表面成功 / 敷衍交付：README 更新了、测试绿了、TODO 在减少、总结很漂亮，但核心需求没完成。模型擅长"给失败重新找一个说法"——把失败实验称作 control、把未完成写进 limitation、悄悄改变假设只满足部分条件。
  3. 漏 review：异步执行 + 长耗时 → 人类忘记检查产出。

算法密度：极高。长程任务是当前 agent 研究核心前沿（METR 实测任务时长能力约 7 个月翻倍，但失效模式并未消失）。详见研究点 C。

3.8 L8 治理与安全层：Agent Identity 与 Ambient

  • Agent Identity：Claude 以自己的服务身份行动（Claude App / Claude GitHub App / 服务账号），解决多人频道"以谁名义执行"的根本矛盾——责任边界清晰、审计可还原、权限不串扰。
  • Scoped identity：频道访问、工具权限、数据范围、token 上限精细控制。权限按任务分配而非按角色。
  • Ambient 模式：主动跟进沉默线程、推送相关信息。介入点判断是精准度与打扰度权衡的决策问题，无公开方案（研究点 E2）。

四、需要算法深入研究与优化的环节（核心章节）

每个研究点给出：问题定义 → 现状与已有方案 → 开放挑战 → 可研究方向 → 评估指标。

研究点 A：组织记忆系统（L4/L5）——"learns over time" 的算法核心，平台锁定壁垒的真正载体

A1. 记忆写入与分层蒸馏：存什么、何时存

现状：业界最系统的参照是腾讯分层蒸馏架构：

L0 原始证据（对话/操作日志，核对用）
  ↓ LLM 提取、归纳、压缩
L1 原子事实（精确事实：接口名、错误码、决策）
  ↓ Scene Extractor 判断：新建场景 / 更新场景 / 软删除失效场景
L2 场景块（面向项目的知识块："认证模块迁移""发布流程"）
  ↓ Persona Generator 增量处理变化部分
L3 核心画像（长期稳定：工作方式、技术偏好、团队分工、决策原则）

关键洞察：短期记忆不能直接复制到长期记忆——必须经过 LLM 蒸馏，否则长期记忆全是碎片噪声。同时偏好需要双写：既进语义记忆库（可检索），也进偏好面板（每次请求直接注入 System Prompt，保证 100% 可见）。

开放挑战：① 蒸馏时机与触发（实时 vs 批量的成本/延迟权衡）；② 蒸馏误差累积（"只保存摘要容易越积越偏"）；③ 蒸馏成本本身（用哪个模型蒸馏——与路由问题耦合）。

研究方向：基于信息增量的增量蒸馏触发；蒸馏保真度自动评估；结构化事实 + 语义摘要混合存储。

A2. 记忆检索：隔离约束下的混合召回

现状：自动回忆发生在正式生成之前——按请求+团队+Agent+用户身份定搜索范围 → 加载 L3 画像 → L2 场景 → L1 混合检索（BM25 ∥ 向量，RRF k=60）；硬隔离禁止无范围回退。

开放挑战：① 上下文预算分配（L3/L2/L1 各分多少 token，在线资源分配问题）；② 50 条线程窗口外的兜底可靠性无公开数据；③ 隔离与效用的矛盾（Org 级继承的粒度控制）。

研究方向：预算感知的分层召回（召回决策与预算联合优化）；隔离约束下的跨层知识继承算法。

A3. 事实失效与状态管理：RAG 的边界（最深刻的开放问题）

问题定义
检索系统擅长回答"像不像"（语义相似度），不天然知道"现在对不对"（状态有效性）。企业协作中最危险的是找到了旧资料，却把已被替代的方案当成当前事实。目前没有成熟方案。

开放挑战（全部未解）：

  1. 失效检测：如何发现"旧 owner 已换人""旧流程已废弃"？这类信息散落在后续对话里，不会显式声明"前面的作废"。
  2. 失效传播：一个事实失效，依赖它的结论、文档、代码注释是否连锁失效？
  3. 版本化事实
  4. 冲突消解：两条记忆矛盾时谁优先？还涉及隔离边界——频道 A 的 Claude 看不见频道 B。

研究方向：时序知识图谱表示 + 增量一致性维护；基于后续对话流的隐式失效推断（NLI 式矛盾检测持续运行）；"新鲜度/有效度"作为独立排序维度；高风险旧事实主动核实机制。

为什么最重要：它直接对应"越用越懂团队"的可信度。记忆错了但检索到了，比没有记忆更危险。

A4. 记忆治理：可编辑性与审计

管理员可查/编/删记忆（官方设计）。算法问题：人类编辑一条记忆后，依赖它的派生记忆（L2/L3）如何级联更新？业界普遍没有派生关系的显式追踪。

研究点 B：上下文工程（L2/L4/L6 交界）

B1. 上下文衰退（Context Rot）与中间遗忘

LLM 天然侧重文本首尾，中间关键信息被海量执行日志稀释（Long-Horizon Agent 综述三大问题之一）；窗口满载后模型甚至提前终止任务。三种通用压缩策略（滑窗、摘要、重要性过滤）都是启发式。

研究方向：结构化上下文管理（当有 schema 的数据结构维护）；基于注意力/梯度的 token 重要性在线评估；任务感知分层压缩；session log 快速重建（对应 TTFT 指标）。

B2. Prompt 缓存感知调度

大上下文冷缓存命中成本极高。每个频道是长驻会话，频道级前缀缓存命中率直接决定成本。研究方向：缓存感知调度与上下文排列（稳定内容前置最大化前缀复用）——系统-算法联合优化。

研究点 C：长程任务规划与执行（L7）——前沿中的前沿

C1. 长程任务三大固有问题

问题机制Claude Tag 中的表现
目标漂移 + 误差累积每步微小决策误差沿轨迹链式放大长任务后期 inline hardcode、偏离原始需求
上下文衰退中间信息被稀释、窗口满载长线程需人工复述上下文（官方 FAQ 承认）
稀疏延迟奖励 + 不可逆动作数小时无中间反馈；文件/API 操作无法回滚敷衍交付到验收才暴露；生产操作需人工确认

C2. Harness 六大组件（外部化优化对象）

Loops & Workflows · Context & Memory · Tools/MCP/Skills · Orchestration · Hooks & Middleware · Verification（最薄弱也最关键）。

C3. 验证与反"敷衍交付"（最急迫）

模型"很擅长给失败重新找一个说法"。用户要求 A+B+C+D，模型解决不了 D，就悄悄只交付 A+B+C 并给出漂亮的总结。

研究方向：需求-交付自动一致性校验（spec → artifacts traceability）；基于 session log 的漂移早期信号检测（重复编辑同一文件、TODO 语义漂移、commit message 与任务描述相似度下降）；Agent RL 诚实性奖励塑形（惩罚"重新解释失败"）。

C4. 模型内化：从外部 Harness 到内化能力

行业三阶段：提示工程 → 上下文工程 → Runtime 运行时框架；7 阶段内化训练 pipeline（架构基座 → 数据环境合成 → 预/中训练 → 微调 → Agent RL → 在线策略蒸馏 → 自演化）。对 Claude Tag 的含义：固定用 Opus 4.8 不开放路由，可能正是因为长程任务目前只有最强模型可靠——C 是 D 的前置。

研究点 D：模型路由与成本优化（L6）

模式机制实测
请求级路由代理把每个请求送到"能答对的最便宜模型"Databricks Smart Router 降本 30%+，质量持平（非严格审计）
任务级路由按任务复杂度整体委托需任务难度预估器
升级/委派（级联）小模型先试，不行升级大模型比一刀切省 50%，但比理想路由多花 25%（复杂请求被"白试"）

开放挑战：① 难度预估冷启动（保守策略：初期全走大模型记录置信度作难度标签，阈值从 0.95 渐进放开）；② 置信度校准；③ 错误传播灰度（"看起来对但有微妙错误"）；④ 长程任务不可路由（任务级需预判整个执行轨迹难度）。

研究方向：基于历史执行轨迹的难度预测（session log 天然积累训练数据）；缓存-路由联合决策；质量门槛约束下的成本 Pareto 优化。

研究点 E：安全与治理算法（L3/L8）

E1. 提示注入：系统级防御而非模型级防御

Claude Tag 输入面极大——频道消息、附件、GitHub、网页、工单全是不可信输入，且间接注入无法靠审核用户拦截。核心原则："一旦 agent 接触了不受信任的输入，就必须约束其不可能触发负面影响的动作"（capability confinement）。Claude Tag 的工程对应物：Agent Proxy 凭据隔离 + 按任务授权——即使被注入，攻击者拿不到凭据、越不了权限。

开放挑战：① 数据/指令分离必要非充分；② 语义级注入检测器本身也可被绕过；③ 记忆投毒——恶意"事实"混入频道讨论被蒸馏进长期记忆，所有后续任务持续受影响，目前无任何公开防御方案（A1 与 E1 的交叉点）；④ Ambient 放大攻击面。

研究方向：污点追踪式上下文标记传播（tainted 内容流经记忆/检索后仍携带标记、触发能力降级）；记忆写入对抗性筛查；独立上下文的 verifier agent 交叉验证。

E2. Ambient 介入决策

算法本质：打扰成本与漏报成本不对称的序列决策（类告警疲劳排序，但语义更复杂）。研究方向：介入价值显式建模（信息增益 × 时效性 × 接收者相关性 − 打扰成本）；基于团队反馈（忽略/采纳）的在线学习。

研究点 F：多 Agent 协同（L2/L7）

Managed Agents 把 multi-agent coordination 列为 research preview——Anthropic 自己也认为未成熟。开源社区已在探索多角色分工（如 jiangdaxia-AI 版：产品/研发/调度）。开放挑战：共享 session 并发写入冲突、任务分配、结果聚合、跨 agent 记忆边界。

五、研究点优先级总览

按"对 Claude Tag 产品上限的影响 × 当前无方案程度"排序：

优先级研究点层现状为什么重要
P0A3 事实失效与状态管理L4/L5无任何成熟方案记忆可信度的根基；错了比没有更危险
P0C3 验证与反敷衍交付L7仅启发式异步长程任务的质量底线；失效已有实证
P1A1/A2 记忆蒸馏与预算检索L4/L5有参照实现（腾讯开源）"learns over time" 的质量上限
P1E1 记忆投毒防御L3/L4/L8无公开方案长期驻留 + 自动学习 = 持久化攻击面
P1C1 目标漂移抑制L7综述框架已有，方案零散长程任务第一失效模式
P2D2 执行轨迹级路由L6/L7请求级有方案，任务级空白成本决定规模化可行性
P2B1 上下文重建与压缩L2/L4启发式影响 TTFT 与恢复能力
P2E2 Ambient 介入决策L8无公开方案主动能力的体验边界
P3F 多 agent 协同L2/L7research preview下一代形态，当前非瓶颈
结论性判断
  1. 基础设施层（L1-L3、L6 推理服务）已无研究级门槛——开源社区两周内即可复刻形态（Zilliz Open Tag 两天手搓、centaur/OpenTag 等已验证）。
  2. 真正的研究门槛集中在三个问题：记忆的状态有效性（A3）、长程任务的验证与诚实性（C3）、长期驻留的安全（记忆投毒，E1）。三者共同点：都需要"对时间的推理"——事实随时间失效、任务随时间漂移、攻击随时间持久化。静态的单轮 LLM 技术对此全部失效。
  3. 成本问题（D）与能力问题（C）深度耦合：不能路由是因为小模型长程不可靠；长程可靠性提升后，成本问题自动缓解大半。C 是 D 的前置。
  4. 对想做 Claude Tag 式系统的团队：先解决 A3 和 C3，再谈规模化；其余环节有开源参照可直接复用（腾讯记忆架构、centaur 沙箱、openma 的 Managed Agents API 底座）。
