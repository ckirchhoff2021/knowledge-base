摘要

飞书数字员工是一种按业务职责划分、长期驻留在飞书单聊与群聊中的 AI 同事。它与"一次性问答机器人"的本质区别在于持续学习：把群里的高噪声消息流沉淀为可检索、可治理、可跨会话复用的长期记忆。本报告参考 Hermes Agent 的记忆架构（有界常驻档案 + 按需会话检索 + 外部 provider）与 Claude Tag 的分层隔离记忆设计，结合业界主流记忆框架（Mem0、Letta/MemGPT、Zep、腾讯 AgentMemory 的 L0-L3 蒸馏管线）的工程经验，给出一套面向飞书数字员工的五层记忆 + 四级隔离架构方案，覆盖写入蒸馏、预算检索、跨群知识提升、用户主动沉淀、遗忘与安全治理的完整生命周期。

1. 背景

1.1 产品形态

飞书数字员工的设计方式类似 Claude Tag：一种业务职责一个数字员工（研发助手、客服助手、运维值班助手……），每个员工拥有自己的身份，可以：

  • 支持单聊（1v1 DM）；
  • 被拉进群聊，可同时驻留多个群；
  • 观察群内其他成员的消息，被 @ 时响应并执行任务；
  • 持续学习，把群里的关键知识沉淀为长期记忆；
  • 主动响应：后台信息充足时识别用户意图、完成定时任务并推送结果；
  • 支持异步长程任务。

1.2 为什么记忆是核心

LLM 本身无状态：每次调用都是把全部历史重新喂进去。这在单轮聊天里勉强可用，但对一个长期驻留、多群并发、异步长跑的数字员工是致命的：

  1. 上下文窗口装不下：一个活跃群每天几百条消息，一周就远超任何窗口。研究表明长上下文中段信息会被模型"看不见"（Lost in the Middle，U 形注意力曲线），塞得越多反而记得越差；超长对话下即使百万 token 上下文的模型记忆能力也会退化（BEAM 基准的结论）。
  2. 成本不可接受：全上下文方案每次调用都重发全部历史。Mem0 论文给出的对比：同样场景下全上下文每次查询约 $0.0039，经记忆层提炼后约 $0.000026，相差约 150 倍（社区转述数据，引用前建议核对原文）。
  3. 跨会话/跨群无法复用：上周群里定下的技术选型、用户的偏好、某次故障的处理经验，新会话必须靠记忆系统找回，否则数字员工永远是"第一天上班的新人"。
  4. 记忆是产品壁垒：Claude Tag 的分析指出，模型可以换，但员工/组织积累的记忆与工作流换不了——"公司记忆"是平台锁定的真正载体。对数字员工同理：记忆质量决定产品上限。

2. 参考架构分析

2.1 Hermes Agent：三层记忆 + 冻结快照

Hermes Agent（97k+ stars 的开源 Agent 框架）的记忆系统是本报告的第一参照系，其三层架构（官方文档 2026-08-27 实测）：

层 载体 容量 注入方式 成本特性
档案层（持久记忆） MEMORY.md（agent 笔记，2200 字符）+ USER.md（用户画像，1375 字符） 有界，满了报错让 agent 自己整理 会话开始时冻结快照注入 system prompt 每轮固定 ~1300 token，但文件稳定 → prompt cache 命中率高
搜索层（会话检索） SQLite + FTS5 全量会话库（state.db） 无限（所有历史会话） 模型按需调用 session_search 工具 免费、~20ms，但依赖模型"想得起来搜"
Provider 层（外部记忆） 可插拔后端（Mem0、Honcho、Hindsight…） 取决于后端 每轮自动 prefetch + 工具按需 语义提取贵但高价值

关键设计决策，均可直接迁移到飞书场景：

  1. 有界 + 硬容量上限：常驻记忆不是越大越好。写满时返回错误并附当前条目，强制 agent 在同一轮内合并/删除旧条目再重试——把"遗忘"内建进写入协议，而不是事后补救。
  2. 冻结快照模式：记忆只在会话开始时注入一次，会话中的写入立即落盘但不改当前 prompt。这是为了保护 LLM 前缀缓存——中途改 system prompt 会击穿缓存。代价是"本会话写、下会话见"。
  3. 写入安全扫描：记忆会被注入 system prompt，因此写入前扫描 prompt injection / 凭据外泄 / 不可见 Unicode 字符——记忆是持久化注入攻击面，不是普通数据库。
  4. 写审批门（write_approval）：可配置为每次写入需人工批准（暂存队列 + /memory approve）。对群聊场景尤其重要——群里任何人说的话都不应无条件成为员工记忆。
  5. memory ≠ session search 的分工：关键事实常驻（贵但永远在线），长尾细节走检索（便宜但按需）。

2.2 Claude Tag：分层隔离 + 状态治理

Claude Tag（Anthropic 的频道级数字员工产品）的记忆设计是本报告的第二参照系（细节来自此前调研报告的知乎转述，非官方公开实现）：

  • 分层隔离：Org → Workspace → Channel 三级，向下继承、不向上泄漏；不同频道的实例记忆完全隔离；不从私密频道汇报。
  • 管理员可治理：可查看、编辑、删除频道/工作区记忆；可创建 scoped identity 精细控制数据范围。
  • 状态 vs 记忆的命题：记忆回答"过去发生过什么"，状态回答"现在以哪个版本为准"。把已被替代的旧方案当成当前事实，是企业记忆系统最危险的失效模式——旧 owner、旧流程、旧 PR 在语义上"很相关"，在状态上已失效。RAG 擅长找"像不像"，不天然知道"现在对不对"。

映射到飞书数字员工：Org → 员工（业务职责）→ 群 → 单聊用户，同样是向下继承不向上泄漏；且必须引入事实时效机制（生效时间/失效标记），否则群里改口的决策会持续污染后续回答。

2.3 业界记忆框架横向对比

框架 核心思想 写入机制 检索方式 对飞书场景的启示
Mem0（arXiv:2504.19413） 即插即用记忆层：LLM 抽取事实 → ADD/UPDATE/DELETE/NOOP 消解 → 向量库 轮后异步流水线 语义检索 本项目已接入字节 MemoryBase 托管的 mem0 服务（memory/ 模块，user/agent/run 三级隔离，异步 job 抽取），可直接作为 L1 事实层后端
Letta / MemGPT（arXiv:2310.08560） LLM as OS：上下文=RAM，外存=磁盘，Agent 用工具自主换页（core memory / recall / archival） Agent 自编辑 工具按需 自编辑记忆透明可审计，但每次换页都是额外 LLM 调用；适合核心画像块的小心维护，不适合高噪声群消息的全量处理
Zep / Graphiti（arXiv:2501.13956） 时序知识图谱：双时间事实（事件时间 + 摄入时间）+ 边失效不删除 摄入时自动抽取实体关系 图遍历 + 混合检索 状态治理的标准答案：旧事实不删、标记失效，"截至某时为真"可查询——直接回应 2.2 的状态命题
腾讯 AgentMemory（开源） L0 原始流水 → L1 原子事实 → L2 场景块（agentic extraction）→ L3 用户画像（5 触发条件自动生成，全局互斥防并发写坏） 分层蒸馏管线 带团队/Agent 范围约束的混合检索（向量 + 关键词，RRF 融合） 分层蒸馏是本方案的骨架来源；"检索必须带范围约束、代码层禁止无隔离回退"是隔离的工程底线
LangMem 语义/情景/程序三类记忆显式分离；热路径（对话中即时写）vs 后台巩固（事后反思写） 双通道 命名空间存储 写入双通道的分工思路：@响应时的即时确认写 + 空闲时批量蒸馏

两个跨框架的共识值得强调：

  • 蒸馏而非复制：短期消息不能直接复制进长期记忆，否则库里全是碎片噪声，检索质量崩塌；必须经 LLM 提取、去重、冲突消解（知乎认知架构文与腾讯 L0-L3 管线结论一致）。
  • memory-as-a-tool：生产环境中"每轮自动检索全部记忆"是成本-质量反模式；让 agent 自己决定何时召回（Mem0 选择性方案中位延迟 0.20s / 准确率 66.9%，优于标准 RAG 的 0.70s / 61.0%——社区转述，建议核对原文）。

3. 方案设计：五层记忆 + 四级隔离

3.1 总体架构

核心命题：用不同的成本换不同的精度（Hermes 记忆系统总览一文的本质之问）。常驻层小而稳（保 cache）、检索层大而廉（按需取）、蒸馏层贵而准（异步跑）。总体架构如图 1：

五层记忆（按认知科学分类：工作/语义/情景/程序/画像，对应 Tulving 经典分类与 Mem-α 的 Core/Semantic/Episodic 分层）：

层 名称 内容 载体 生命周期 注入方式
M0 工作记忆 当前任务上下文：@响应线程的近窗消息、长程任务的中间状态 会话内 prompt + 任务状态表（Redis/PG） 会话/任务级 直接进 prompt
M1 语义记忆（事实） 从群消息蒸馏的客观事实：决策、结论、口径、配置、人员分工 mem0/MemoryBase（本项目已接入） 长期，带时效字段 按需检索 + Top 偏好常驻
M2 情景记忆（场景） "某次故障如何排查"、"某需求的讨论过程"等场景块，含时间线与来源链接 向量库 + 元数据（来源消息 ID/群/时间） 长期，时间衰减 按需检索（召回时附来源）
M3 程序记忆（技能） 可复用的做事方式：SOP、定时任务模板、报告格式 Skill 文件（Markdown，人类可读可编辑） 长期，版本化 命中触发时加载
M4 画像记忆 员工级人设 + 每用户偏好面板 有界 Markdown（仿 MEMORY.md/USER.md） 长期，有界硬上限 冻结快照常驻注入

偏好双写原则（认知架构文的关键洞察）：用户偏好既进 M1 语义库（可检索），也进 M4 偏好面板（每次请求直接注入）。只靠检索召回，会出现"用户说过用 Java、下次却推荐 Python"——检索可能漏，常驻不会。

四级隔离（对应 Claude Tag 的 Org > Workspace > Channel，向下继承、不向上泄漏）：

级别 范围 内容举例 可见性
S0 员工级 该业务职责的数字员工全局 人设、业务 SOP、跨群提升的知识 员工所有会话
S1 群级 单个群 该群的决策、项目状态、群规 仅本群会话
S2 单聊级 员工与某用户的 DM 个人偏好、私人委托 仅该用户会话
S3 会话级 单次任务/线程 工作记忆 本次任务

隔离的工程底线（腾讯 AgentMemory 的经验）：检索必须带范围约束，代码层禁止"无隔离回退"——任何 search 调用必须携带 employee_id + scope，服务端按 scope 过滤，绝不允许"查不到就放宽范围"。跨群检索（§3.5）是唯一受控的例外通道，且要过审批。

3.2 写入通道：热路径 + 冷路径

借鉴 LangMem 的热/冷双通道与腾讯的阈值触发：

热路径（即时、@响应内）：

  1. 用户主动沉淀（设计规范明确要求）：用户说"记住：发布前必须过安全扫描"→ 员工解析为结构化事实 → 当场复述确认 → 写入对应隔离级（默认群级，用户可指定"这是大家共用的"则走提升流程）。主动指令绕过自动蒸馏的不确定性，是最高置信度的写入来源。
  2. 任务结果回写：一次 @任务成功完成后，把"任务-方法-结果-踩坑"四元组写入 M2 情景记忆（对应"能把结果和失败经验写回知识库才算能干活的 Agent 员工"的验收标准）。

冷路径（异步、后台）：

  1. 观察蒸馏：员工未被 @ 时也观察群消息（产品能力之一）。后台定时（如每 30 分钟/每 200 条）对消息流跑蒸馏管线：
  2. 粗筛（小模型/规则）：过滤闲聊、表情、灌水；
  3. 精炼（大模型）：提取候选事实，标注类型（决策/口径/分工/配置/待办）、置信度、来源消息链接；
  4. 消解（mem0 式）：与已有记忆比对，执行 ADD / UPDATE / DELETE / NOOP；UPDATE 时旧值不删，标 valid_until（Zep 双时间思路）。
  5. 画像巩固：仿腾讯 L3 的触发条件（冷启动/攒够 N 条新记忆/显式请求），用全局互斥锁串行更新 M4 画像，防并发写坏。

写入门控（所有通道共用，缺一不可）：

  • 安全扫描：prompt injection 模式、凭据/密钥、不可见 Unicode（仿 Hermes 写入扫描）；
  • 去重：语义等价检测，重复则合并；
  • 置信度分流：高置信直接入库；中低置信进待审队列，员工下次被 @ 时向相关用户求证（"我理解以后 X 都按 Y 办，对吗？"）——这是群聊场景区别于个人助手的关键：多人环境里，一个人的发言不等于团队共识。
  • 审批模式可配置：高敏群（如涉及人事/财务）可整体开启 write_approval，所有自动写入走人工批准（仿 Hermes /memory pending 暂存审批）。

3.3 遗忘与状态治理

记忆系统最容易犯的错是只增不减。遗忘机制：

  • 时效失效：决策类事实带 valid_until 或被 UPDATE 时标记 superseded_by；检索默认只返回当前有效事实，历史版本可追溯（回应"状态 vs 记忆"命题）；
  • 使用衰减：长期未被检索命中的记忆降权，LRU 式定期归档（Codex Selection Diff 的思路：记忆不是累积状态，而是持续选择的结果）；
  • 主动整理：M4 画像写满时报错，强制员工合并/删除条目（Hermes 机制）；后台周任务跑一次全库"重审"（哪些已被新事实取代）。

3.4 检索与注入：预算控制

@响应时的上下文组装顺序（利用首因/近因效应，关键信息避开中段盲区）：

[system prompt]
  ① M4 员工人设 + 当前群规（常驻，冻结快照）
  ② M4 该用户偏好面板（常驻）
  ③ M0 任务线程近窗消息（工作记忆）
  ④ 按需召回：memory_search 工具返回的 M1/M2/M3 片段
     （混合检索：向量语义 + 关键词，RRF 融合；
       最相关片段放开头，当前问题放结尾）
  ⑤ 当前用户消息（结尾，近因优势）

检索预算：单次召回总延迟目标 ≤500ms（并行 fan-out，不串行）；注入总量设 token 上限（如 4K），超出按相关度截断。默认 memory-as-a-tool（agent 自决何时搜），仅对明确引用历史的提问（"上次那个方案……"）做系统侧预召回兜底——拉式记忆的固有弱点是"想不起来搜"，需要 system prompt 引导语 + 兜底双保险。

3.5 跨群聊检索：受控的知识提升通道

一个员工同时驻留多个群（产品形态），知识复用有两种方向：

向上提升（群 → 员工级）：某群沉淀的知识被判定为"业务通用"（如通用排障经验、公司级口径）时，走提升流程：

  1. 蒸馏管线给候选事实打 promotable 标记（判定依据：不含该群特有的人员/项目实体、属于通用流程或口径）；
  2. 员工向群管理员发起确认（卡片消息，附原文来源）；
  3. 批准后复制为员工级记忆（S0），保留来源群引用；原群级副本不动。

横向检索（群 A 会话查群 B 知识）：默认禁止（隔离底线）。仅两种受控例外：

  • 同一用户同时在群 A 和群 B 时，其 S2 单聊级记忆天然跨群可见（跟人走，不跟群走）；
  • 显式授权：群管理员可把自己的群标记为"知识可被本员工的其他群检索"（如上游团队群对下游开放），检索时结果强制附来源群标注，防止"记忆串味"（群 A 的人误以为某结论来自本群讨论）。

这与 Claude Tag 的"向下继承不向上"一致：默认隔离是硬边界，共享必须显式授权且留痕。

3.6 主动响应与定时任务的记忆支撑

主动响应（产品能力：后台信息充足时识别意图、完成定时任务、推送结果）依赖两类记忆：

  • 意图触发：订阅式记忆——蒸馏时若发现"待跟进"类事实（如"等测试报告出来再评估上线"），生成带触发条件的观察项（trigger：某事实被更新/到期时间到）；条件满足时员工主动在群里跟进。这本质是给记忆加订阅能力，需要事实带 watch 字段。
  • 定时任务：M3 程序记忆存放任务模板（如"每周五汇总本周各群关键决策"），调度器按模板执行，结果推送回群。任务执行日志回写 M2，形成"上次汇总说了什么"的连续性。

4. 结论与选型建议

  1. 骨架选"分层蒸馏管线"（腾讯 L0-L3 式）而非单一向量库：群消息是高噪声流，直接入向量库会让检索质量随时间崩塌；蒸馏（提取-消解-时效）是质量的来源。
  2. 后端复用已接入的 MemoryBase/mem0 服务作为 M1 事实层（本项目 memory/ 模块，user/agent/run 三级隔离正好映射 用户/员工/任务），在其上补 scope、valid_until、superseded_by、source 元数据即可；M2 情景层与 M4 画像层建议自建（前者要来源链接与时间线，后者要有界文本 + 冻结注入）。
  3. 常驻层严格有界（画像 ≤2-3K 字符）+ 冻结快照注入，是成本与 prompt cache 的双重最优解；一切"历史回溯"走检索工具，不进常驻层。
  4. 隔离先于功能：先落地四级 scope 与服务端强制过滤，再谈跨群共享；共享通道必须显式授权、强制来源标注、全程留痕。
  5. 落地节奏：阶段 0（2 周）单群 PoC——只做用户主动沉淀 + 任务回写两条热路径，用 200-500 条脱敏黄金数据测召回（Recall@5 ≥85%、引用正确率 ≥95% 参照 MemOS 落地路线）；阶段 1 加观察蒸馏冷路径与审批门控；阶段 2 才开跨群提升与主动响应。任何阶段未过门禁不扩大数据范围。

5. 注意事项与风险

风险 说明 缓解
记忆投毒 恶意成员把伪事实说进群，等它被蒸馏进长期记忆后所有后续任务持续受影响——持久化的 prompt injection，比单次注入危险得多 写入安全扫描 + 置信度求证 + 高敏群审批模式；来源留痕支持事后追溯删除；删除必须覆盖全部派生索引
一人发言 ≠ 团队共识 群聊里少数人声音大，蒸馏容易把个人观点写成团队决策 决策类事实要求多来源确认（≥2 人或管理员发言）；低置信进待审队列向群求证
状态失效 旧决策语义相关但已过时，被召回后误导 valid_until/superseded_by 双时间字段；检索默认 only_current；回答引用时带时间戳
隐私边界 员工观察群消息的合法性、DM 内容不外泄 观察范围明示（员工进群时声明）；S2 单聊记忆物理隔离、不提升；高敏群可关闭观察蒸馏只保留 @响应
删除不彻底 只删主记录，向量索引/备份仍可召回 删除走全派生链（主记录+向量+派生画像引用），并提供删除验证
蒸馏幻觉 LLM 提取出消息里没有的"事实" 每条记忆强制保留 source 消息引用；回答时附来源，用户可点开核对；引用正确率纳入评测门禁
多写者冲突 同一员工多群并发触发画像更新 画像层全局互斥（腾讯 L3 经验：concurrency=1 + pending 去重）；mem0 服务端本身按 job 异步串行消解
成本失控 观察蒸馏对全量消息跑大模型 粗筛用小模型/规则先砍掉 80% 噪声；蒸馏走空闲批处理；按群活跃度分级频率
